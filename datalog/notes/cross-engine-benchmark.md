# Two engines, one corpus — `datalog` vs `tsdl` measured

Long-form backing for the *Performance* → **Profile the engine** ROADMAP item, and
the second entry in this project's performance record after
[`performance-baseline.md`](performance-baseline.md). That file measured this engine
alone against a fact base that no longer exists; this one measures it against
`~/code/tsdl` on a corpus that regenerates from a script.

**Snapshot, not a live reference.** Measured **2026-08-17**, `datalog` at `0356b04`,
`tsdl` at `fe8dae2`. AMD Ryzen 7 5700G (16 threads, 30 GB) — the same machine as
`performance-baseline.md`, so the two files' numbers are comparable. rustc 1.96.1,
`cargo build --release` with default features; Node v26.5.1 against `tsdl/dist`.
Wall clock from `perf_counter` around the whole process, peak RSS from
`/usr/bin/time -f %M`, best of 3 after a warmup, 120 s timeout. Run-to-run spread
under 2% except at the millisecond floor.

## What this is not

`tsdl`'s own documents name evaluator performance an **explicit non-goal** and ship
naive evaluation deliberately, over a stated semi-naive hazard (under annotations,
rediscovering a tuple is not a no-op). "The Rust one is faster" is therefore not a
finding, and nothing here is a criticism of that project.

What *is* new information for both is the **shape** of the separation — whether the
gap is a constant factor an implementation could close or an exponent only a
different algorithm reaches — and, unexpectedly, the two places where this engine is
the one that behaves badly.

## Method: one corpus, both engines, no dialect variants

The corpus is generated by a script into 26 `.dl` files, each fed **byte-identical**
to both engines. That is possible because the dialects overlap almost exactly; the
generator stays inside the common subset by using integers and symbols only, `%`
comments, and making every query a bare atom over a rule head — which avoids the
four places the dialects genuinely differ (this engine's strict int/float split vs
tsdl's single `number`; `count distinct`; the temporal types; and tsdl's
`unnamed-answer` rule, which refuses the multi-atom query bodies §14 prints
`answer/N` for).

Three things gate the timings, and all three passed:

- **Both engines agree.** All 23 programs that ran on both produced byte-identical
  answers after sorting. This is a free differential test between two independent
  implementations of the same language, and it is the first time one has been run.
- **Both agree with a third party.** The generator computes each program's expected
  answer count analytically or by a Python BFS — never by running either engine,
  which would make the oracle circular. No mismatches.
- **The harness is measuring the engines.** tsdl's `chain_200` landed at 15.79 s
  against ~16 s measured independently by a different route before the harness
  existed.

`tsdl` has no CLI, so its runner is ours: ~20 lines importing `dist/index.js` and
calling `run(src)`. It deliberately does **not** reuse `tools/experiment/dl.ts`,
which registers a fixture as host relations and forces the `LINEAGE` semiring —
both confounds. The default `run(src)` is tsdl's cheap `BOOLEAN` path.

## What the curves say

**The front end is the same order; only evaluation separates.** Startup subtracted,
this engine parses ~480 k facts/s against tsdl's ~110 k — about **4×**, the kind of
gap a language runtime explains. Every ratio above 10× in this document comes from
the fixpoint, not from reading the program. That matters because it locates the
whole difference in the part both projects call the engine.

**The chain separation is an exponent, not a constant.** Log-log slope between
adjacent sizes:

| | 50→100 | 100→200 | 200→400 | 400→800 |
|---|---|---|---|---|
| this engine | n^0.93 | n^2.42 | n^2.40 | n^2.89 |
| tsdl | n^2.73 | n^3.76 | — | — |

Closure output on a chain is itself n², so ~n^2.4 is near the output bound and
~n^3.8 is a full extra factor of n above it. That is semi-naive vs naive doing
exactly what the textbook says, measured: the delta saves re-deriving the whole
relation each round, and the saving is an exponent. It also confirms tsdl's own
2026-08-04 note that its remaining exponent is O(n⁴)-ish for a chain of n and that
what they fixed earlier was the constant.

**This engine's throughput is 5–14× better than `performance-baseline.md` recorded**
— 85 k–270 k derived tuples/s here against that file's headline ~15 k/s. The
workloads differ in one way that file already flagged as its top hypothesis: those
facts were long Rust identifiers (`engine::naive::apply_builtins`), these are `n123`.
Same engine, same machine, ~10× the throughput on short values is **consistent with
value representation being the cost**, which is the interning / `Rc<str>` lead that
note asked the profile to confirm or kill. It is evidence for it, not the profile.

Throughput also *degrades* with size — 273 k tuples/s at n=100, 205 k at 200, 156 k
at 400, 85 k at 800 — while RSS reaches 458 MB for 320 k tuples (~1.5 KB/tuple, in
the same range as the note's 2.9 KB/pair for longer strings). The engine slows as it
fills memory.

## Two places this engine is the bad one

Both are ours, both are new, and neither is visible without a second engine to
notice them against.

### 1. Aggregation goes superlinear in the aggregated relation, and loses outright

`agg` at 50 000 rows is the only cell in the corpus where tsdl wins — 3.69 s against
our 3.77 s — after leading 5× one size earlier. Between those two sizes this engine
got 23× slower for 2.5× the data; tsdl got 5× slower.

Holding one variable at a time (output size held constant, so this is not printing):

| rows | groups | wall |
|---|---|---|
| 20 000 | 400 | 0.158 s |
| 30 000 | 400 | 0.354 s |
| 40 000 | 400 | 1.184 s |
| 50 000 | 400 | 1.513 s |
| 20 000 | 600 | 0.209 s |
| 20 000 | 800 | 0.249 s |
| 20 000 | 1 000 | 0.305 s |

**Groups scale sublinearly; rows scale ~quadratically.** 2.5× the rows at a fixed
group count costs 9.6×. The shape is what you get if each group's aggregate goal
rescans the whole aggregated relation rather than reaching it through the group key
— cost in the product of the two, with something worse on top. That is a hypothesis
the profile should confirm; the measurement is that `count { I | item(G, I) }` does
not scale with `item`.

### 2. `sparse_800` is a 22× cliff and 1.2 GB

2.90 s at n=400 → **65.14 s** at n=800, for 2× the nodes, at 1 187 MB peak. The
chain at the same node count is 3.78 s. The difference is cycles: the random graph's
closure has many derivations per fact, and every one of them is recorded. This is
the `reaches(A,B), reaches(B,A)` non-termination from `performance-baseline.md`
appearing in a milder, finite form — and it is the shape most like a real dependency
or call graph.

## Confounds, stated

- **Provenance is not symmetric, and it is the largest confound here.** This engine
  records every derivation unconditionally with no flag to disable it;
  tsdl was measured on `BOOLEAN`, which records none. Running tsdl under `LINEAGE`
  brackets the other side:

  | program | BOOLEAN | LINEAGE | overhead |
  |---|---|---|---|
  | join_1000 | 0.206 s | 0.278 s | 1.35× |
  | agg_5000 | 0.199 s | 0.255 s | 1.28× |
  | chain_200 | 17.07 s | 28.44 s | 1.67× |
  | negation_100 | 0.453 s | 2.86 s | 6.31× |
  | sparse_100 | 0.689 s | 9.04 s | **13.1×** |

  So the tables **understate** this engine: it is paying a provenance cost on every
  row that its opponent is not, and on exactly the cyclic shapes where that cost is
  worst. It also independently supports `performance-baseline.md`'s hypothesis 1 —
  a second engine measuring its own recorder finds 13× on a dense cyclic graph, and
  ours is the shape (`sparse_800`) that blew up. **Measuring our recorder's share is
  now the highest-value thing the profile can do**, and it still needs a temporary
  build, since there is no flag.
- **Node's JIT is cold in every process.** Honest for a CLI, pessimistic for a
  library that is meant to be embedded and called repeatedly. tsdl's floor is ~88 ms
  of startup against our ~4.5 ms; at the smallest sizes that floor *is* the ratio.
- **RSS is not comparable at the low end.** Node's baseline heap is ~95 MB before
  any Datalog runs, so tsdl's memory column only becomes meaningful above ~200 MB.
- **tsdl has no CLI**, so its runner is ours and any inefficiency in it is charged to
  them. It is 20 lines and does nothing but read a file, call `run`, and print.
- One corpus on one machine, synthetic graphs, no imports (the corpus is inline
  facts, so §13's import path is untested here and `performance-baseline.md` remains
  the only measurement of it).

## What this leaves for the profiling item

The ROADMAP item asks for a repeatable benchmark before optimizing anything. This is
one, and it lives at **`~/datalog-cross-engine-bench-2026-08-17/`** — outside the
repo, as `~/datalog-source-analysis-2026-07-27/` was. Four scripts, 44 KB: the corpus
is not stored but regenerates deterministically from a fixed seed in under a second,
which answers `performance-baseline.md`'s "the fact base needs a home" in the
cheapest of the three ways that file listed (generate a synthetic graph rather than
commit a fixture or an extractor). Moving it into the repo is a decision this note
does not take — it would need a `tsdl` checkout to run in full, though the generator
and the `datalog` half stand alone.

In priority order, what it says to look at:

1. **The derivation recorder**, now with a second engine's 13× as corroboration.
2. **Aggregation's scan over the aggregated relation** — the one shape where this
   engine is beaten, and a clear enough measurement to act on.
3. **Value representation**, which the short-symbol throughput gap points at again.
4. **Cyclic graphs specifically** — `sparse_800`, not the chain, is where the engine
   falls over, and the chain is what everyone benchmarks.
